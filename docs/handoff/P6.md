# P6 integration handoff

P6 edits only API/sync, service wiring and its assigned screens. Core/offline/backend were not edited.

## P2: recovery and LAN browser blockers (observed against running fake backend)

1. `POST /v1/vouchers/issue` must be idempotent by authenticated device + orderId: replay must return the exact original signed vouchers. A successful ₹100 issuance followed by the same request currently returns `409 NO_UNISSUED_COLLATERAL`. If the process dies or the response disappears after server issuance but before P6 persists its response, there is no API to recover those funded vouchers. P6 persists orderId before opening payment, issued items before wallet writes, and deduplicates wallet/ledger writes. The server response-loss window cannot be repaired solely in mobile-owned files.
2. Add an idempotency key for onramp creation or an authenticated lookup by client attemptId. A process death between server order creation and receipt/persistence of orderId currently leaves an orphan order. P6 resumes known orderIds without creating another order.
3. Helmet's `upgrade-insecure-requests` stalls the mock UPI Pay form over `http://10.125.221.169:3001`; the identical order submitted successfully through `http://localhost:3001`. The observed response CSP contains `upgrade-insecure-requests`. Configure a development-only HTTP LAN policy or provide a trusted HTTPS URL; keep production CSP strong. P6 normalizes the gateway's relative `/mock-upi/...` paymentUrl against the selected backend URL.
4. Existing `.env` selects CHAIN_MODE=chain, but `backend/src/chain/index.ts` still throws NotConfigured. P6 launched an isolated fake-mode process on port 3001 with DB_PATH in TEMP, without changing existing configuration or DB data.

## P2/P5: settlement startup

P5's new `settleRoutes`, `settlementWalletRoutes` and jobs need integration into backend app/context/startup by the owner of those files. At P6 inspection, backend app did not mount `/v1/settle`. Mobile posts batches of at most 16 items, validates exact per-item response coverage, journals responses before acknowledging ReceivedStore, and retains pending receipts on request/validation failure. Payout completion is shown only from backend payout statuses, never inferred from status-0 redemption.

## P4: request IDs and reset API

P7 is committed and wired into `realServices.offline`. Core `wallet.markSpent` uses bytes32 voucherIdSchema for the SPEC's bytes16 reqId; core `schema.paymentProofSchema` likewise requires bytes32 reqId. Both payer spend and received proof persistence need bytes16 schemas and regression tests. P6 does not edit core/offline and does not pad or mutate protocol IDs.

Please expose a production core reset API that atomically coordinates wallet/receipt/ledger/config deletion, SecureStore identity/anchors/clock deletion and in-memory state invalidation. P6's explicit confirmed reset adapter currently clears the known core tables/keys and reloads the JS runtime; it retains the DB encryption key for the now-empty open SQLCipher DB. Any new core storage keys must be reflected there until the API exists.
