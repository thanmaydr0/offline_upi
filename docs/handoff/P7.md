# P7 OfflineFlows handoff

## P6 — services/index.ts wiring (P7 does not own this file)

Import `offlineFlows` from `../offline` and set `realServices.offline = offlineFlows`.
Remove the TODO and any Home gating which says P7 is unavailable. Keep mock wiring
for the mock service bundle as needed; Pay/Receive deliberately use the real local
controller directly so a mock can never display a fake verified receipt.

`mobile/src/offline/index.ts` exports a ready singleton and an injectable
`OfflineFlowController`. No ApiClient or network calls exist in the controller.
Cache validated `/v1/config` through core `cacheServerConfig` before going offline;
it includes issuerAddress, vaultAddress, chainId, revokedDevices, and the limits
`maxSingleOfflinePaymentPaise` / `merchantMaxUnsettledPaise`. Both phones need
initialized keys, cached config and trusted server time. Payer needs issued vouchers.

Core `markSpent` already appends `offline_spend`; the singleton sets
`walletAppendsSpendLedger: true` to avoid doubling the ledger's rolling spend.
Other injected wallets default to an explicit controller ledger append.

## P4 — blocking protocol mismatch in core/wallet.ts

`SqliteVoucherWallet.markSpent` parses `reqId` with `voucherIdSchema` (bytes32),
but SPEC 5 requires bytes16. P7 passes the original 16-byte request ID unchanged.
Please add/use a bytes16 request schema and a regression test using a real
PaymentRequest reqId. Until fixed, production payment fails before proof display.
P7 does not modify core or silently change the wire protocol.

## Security and UX behavior

- Open requests and expiry persist in the encrypted core database (`p7:open`).
- Requests expire at 300 seconds with no grace period; signed vouchers/payment
  deadlines use shared verification and cached skew (default 300 seconds).
- Committed request markers persist (`p7:paid:<reqId>`) before markSpent.
  Crash/storage failure after commitment refuses regeneration, even if no proof
  was displayed. A lost proof cannot be recovered in this implementation; online
  reconciliation is necessary. No hardware rollback resistance is claimed.
- One biometric batch call; signatures are verified before committing spending.
  Proof output returns only after markSpent and its ledger append succeed.
- Shared verifyProof plus aggregate payment cap checks precede ReceivedStore.
- Risk uses local total pending exposure: <=75% low; >75% through 90% medium;
  >90% through cap high. Over-cap is rejected. These labels cannot detect another
  offline payee's acceptance of the same vouchers or fresh online revocations.
- QR input limited to 1800 characters/frame, 128 frames, 128000 assembled
  characters and 128 vouchers. Identical duplicate frames are idempotent;
  conflicting duplicates reset scanning. Frames from separate proofs can only
  fail verification; there is no transport-level frame-set identifier in SPEC 5.
- Camera is unmounted on blur/background; torch and QR pause/step controls exist.
  No hardware focus, brightness or scan-speed guarantees are claimed.
